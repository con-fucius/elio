# Technical Implementation Specification — KE Digital Work Cards

**Status:** Baseline to implement
**Scope:** Kenya pilot
**Initial use cases:** hospital field workers, marketing officers, debt-collection officers
**Architecture:** PWA + API modular monolith
**Native Android:** explicitly out of Phase 1
**Primary principle:** operationally reliable under poor connectivity and human/organisational stress

This document supersedes the earlier stack brainstorming. Where an earlier recommendation conflicts with this document, this document wins.

The Kenya-specific privacy baseline is the Data Protection Act 2019 and associated 2021 regulations. ODPC explicitly treats health data as requiring heightened protection and provides sector-specific health-data guidance; DPIAs are required where processing is likely to create high risk. ([Data Protection Office][1])

# 4. State machines

No feature may invent its own arbitrary status logic.

## WorkItem

Initial state machine:

```text
CREATED
  ↓
ASSIGNED
  ↓
ACCEPTED
  ↓
IN_PROGRESS
  ├──→ BLOCKED
  │      ↓
  │   IN_PROGRESS
  │
  └──→ SUBMITTED
           ↓
        REVIEW_REQUIRED
           ├──→ ACCEPTED
           └──→ REJECTED
                    ↓
                 IN_PROGRESS

ACCEPTED
   ↓
COMPLETED
```

Terminal states must be explicitly defined.

Illegal transitions must be rejected server-side.

### Acceptance criteria

* Every transition has an explicit predecessor.
* Every transition has an actor authorization rule.
* Every transition is auditable.
* Illegal transitions produce deterministic errors.
* Concurrent transitions cannot silently overwrite one another.
* Every transition has automated tests.

# 5. Command model

The client never directly mutates authoritative business state.

Examples:

```text
AcceptAssignment
StartWork
SaveWorkDraft
SubmitWork
CompleteWork
RaiseException
AttachEvidence
RequestReview
WithdrawSubmission
```

Command structure:

```text
command_id
idempotency_key
tenant_id
actor_id
device_session_id
aggregate_id
command_type
schema_version
client_sequence
client_created_at
payload
```

Server processing:

```text
authenticate
→ authorize
→ validate schema
→ validate aggregate state
→ validate policy
→ validate invariants
→ execute transaction
→ write business state
→ write event
→ write audit
→ write outbox
→ return authoritative result
```

All material mutations occur inside a database transaction.

---

# 6. Idempotency

Every mutating command requires an idempotency key.

Database uniqueness:

```text
UNIQUE (
    tenant_id,
    actor_id,
    idempotency_key
)
```

Server stores:

```text
request_hash
status
result
created_at
```

If the same request is retried:

```text
same key + same payload
→ return original result
```

If:

```text
same key + different payload
→ reject
```

### Required tests

* duplicate simultaneous requests
* retry after server commit
* retry after response loss
* retry after timeout
* duplicate offline commands
* duplicate commands from two browser tabs

---

# 7. Offline architecture

The PWA uses:

* Service Worker for application shell/offline resources
* IndexedDB for structured local state
* local command queue
* synchronization engine

PWAs support offline operation through service workers and structured client-side storage such as IndexedDB. Background execution is possible but browser-controlled and therefore less deterministic than native mobile execution. ([MDN Web Docs][3])

Therefore:

**We do not depend on background synchronization being guaranteed.**

When the application resumes, it must detect pending work and synchronize.

Local state:

```text
LocalWork
LocalAssignment
LocalPolicy
LocalEvidence
PendingCommand
SyncCursor
SyncError
```

---

# 8. Sync protocol

The synchronization protocol is explicitly designed rather than using generic CRUD.

## Upload

```text
POST /sync/commands
```

Client sends a bounded batch of commands.

Server responds:

```text
accepted
rejected
requires_review
conflict
retryable
```

## Download

```text
GET /sync/changes?cursor=X
```

Server returns authoritative changes relevant to that actor/device/tenant.

Client advances cursor only after durable local persistence.

### Critical invariant

Never:

```text
receive server response
→ advance cursor
→ crash before local persistence
```

Instead:

```text
receive
→ persist transactionally
→ advance cursor
→ commit
```

---

# 9. Conflict strategy

We explicitly reject generic "last write wins."

Conflict handling depends on domain semantics.

Examples:

```text
description changed
→ potentially mergeable

assignment revoked
→ server authoritative

work completed twice
→ idempotent/rejected

policy changed while offline
→ evaluate compatibility

financial outcome changed
→ never silently merge
```

Every conflict category gets an explicit resolution policy.

Unknown conflict:

```text
→ REVIEW_REQUIRED
```

Never silently discard data.

---

# 10. Time model

Every material event carries:

```text
client_time
server_received_time
server_event_time
```

Device time is **not authoritative**.

The system must never infer legal/business chronology solely from client timestamps.

Client time remains useful as provenance.

---

# 11. Evidence model

Evidence is first-class.

```text
Evidence
  id
  work_item_id
  type
  captured_by
  device_session
  captured_at_client
  received_at_server
  storage_reference
  checksum
  metadata
  verification_status
  retention_class
```

Statuses:

```text
CAPTURED
UPLOADED
VERIFIED
REJECTED
DISPUTED
EXPIRED
```

Evidence must never automatically equal truth.

For example:

```text
GPS → location evidence
photo → visual evidence
worker statement → declaration
server record → system observation
```

The UI must not describe these as independently verified facts unless they actually are.

---

# 12. Location

Location is **event-scoped**, not continuously tracked.

Default:

```text
no continuous tracking
```

Where location is genuinely necessary:

```text
capture location at relevant action
```

Store:

```text
latitude
longitude
accuracy
captured_at
source
purpose
```

No location collection without a documented purpose.

ODPC's registration system itself treats GPS location data as a sensitive category requiring explicit handling. ([Data Portal][4])

---

# 13. Authority model

Authorization is:

```text
Actor
+ Tenant
+ Role
+ Assignment
+ Work state
+ Action
+ Context
+ Policy version
→ decision
```

Decision:

```text
ALLOW
DENY
REQUIRE_REVIEW
```

Policy versions are immutable.

Every authoritative decision records:

```text
policy_id
policy_version
decision
reason_code
```

No business-critical authorization logic may exist only in React.

---

# 14. Human override

Override is a controlled state transition, not an administrator bypass.

Required:

```text
override_actor
reason_code
free_text_reason where required
original_decision
new_decision
policy_version
timestamp
```

Sensitive overrides require elevated authorization.

Overrides are separately measurable.

A high override rate is treated as a system-health signal.

---

# 15. Audit architecture

Business audit is separate from logs.

Audit records:

```text
actor
tenant
action
aggregate
before_state
after_state
policy
reason
timestamp
correlation_id
source
```

Normal users cannot modify or delete audit records.

Audit must survive ordinary application errors.

---

# 16. Database design rules

Mandatory:

* foreign keys
* unique constraints
* check constraints
* NOT NULL where semantically required
* explicit indexes
* tenant scoping
* optimistic concurrency
* transactions around business mutations

Forbidden:

* application-only uniqueness assumptions
* unbounded JSON blobs for core entities
* deleting records required for audit
* implicit cascade deletes for sensitive records
* database tables without ownership semantics

Before production processing:

### Data inventory

For every data element:

```text
field
purpose
classification
lawful basis
controller
processor
access
retention
deletion

```

Kenya's framework requires lawful, fair and transparent processing, purpose limitation, data minimization, accuracy, retention limitation and safeguards for transfers outside Kenya. ([Data Protection Office][5])

### DPIA

A DPIA is mandatory for processing likely to create high risk and must assess processing, necessity/proportionality and risks. ([Data Protection Office][6])

For the pilot:

**health use case → DPIA before live patient data.**

Debt collection:

**separate privacy/legal review before production customer data.**

# 23. Health boundary

The hospital module must initially avoid becoming an EMR.

Allowed:

```text
worker assignment
facility visit
service checklist
operational observation
non-clinical evidence
task completion
exception
```

Not initially:

```text
diagnosis
clinical decision support
prescription
clinical record replacement
patient longitudinal record
medical-device control
```

If patient-identifiable health information becomes necessary, the security/privacy boundary changes and must undergo explicit review. ODPC's health-data guidance specifically addresses hospitals, health workers, CHVs, EMRs/EHRs and other health-data systems. ([Data Protection Office][7])

```text
→ capture permitted evidence

```

* customer data minimization
* no fabricated visit completion

## C. Debt collection

Example:

```text
Receive assigned account
→ authorized contact attempt
→ record outcome
```

No:

* harassment workflows
* unauthorized third-party disclosure
* arbitrary contact

# 25. Integration architecture

External systems are adapters.

```text
Domain
  ↓
Integration interface
  ↓
Adapter
  ↓
External system
```

Never allow external APIs to leak throughout the domain.

Integration delivery:

```text
PENDING
→ SENT
→ ACKNOWLEDGED
```

Failures:

```text
RETRYABLE
PERMANENT_FAILURE
REQUIRES_REVIEW
```

Transactional outbox:

```text
DB transaction
  ├── business state
  ├── audit
  └── outbox event

worker
  ↓
external integration
```

This prevents:

```text
database committed
but external event lost
```

# 28. Critical invariants

These become automated tests.

### INV-001

A user cannot access another tenant's data.

### INV-002

An unauthorized actor cannot execute a command.

### INV-003

A material command is processed at most once semantically.

### INV-004

A successful server transaction cannot lose its audit record.

### INV-005

A successful business mutation cannot lose its outbox event.

### INV-006

Offline commands survive application restart.

### INV-007

Sync retries cannot duplicate business effects.

### INV-008

Client timestamps cannot override server authority.

### INV-009

Illegal state transitions are rejected.

### INV-010

Unknown conflicts never silently overwrite authoritative state.

### INV-011

Deleting a business record cannot destroy required audit evidence.

### INV-012

Policy changes cannot silently invalidate historical decisions.

### INV-013

Sensitive data cannot appear in ordinary application logs.

### INV-014

A compromised/expired session cannot continue indefinitely.

### INV-015

PWA operation does not require continuous connectivity.

# 33. Final implementation order

Do **not** build the three verticals simultaneously.

The sequence should be:

```text
Architecture
   ↓
Platform
   ↓
Identity/Tenancy
   ↓
Work engine
   ↓
Offline/sync
   ↓
Evidence/audit
   ↓
Operations console
   ↓
Hospital vertical
   ↓
Hostile testing
   ↓
Pilot
   ↓
Marketing vertical
   ↓
Collections vertical
```

The **hospital workflow should be the first real vertical**, because it forces us to confront privacy, evidence, authorization and offline operation early. The marketing workflow then tests whether the platform generalizes without healthcare-specific complexity. Collections comes last because its legal, privacy and behavioural constraints warrant separate validation.

The PWA decision is also now explicit: service workers and IndexedDB give us the necessary offline primitives, but background execution is not guaranteed by browsers, so the synchronization protocol must remain correct when background execution does not happen. ([MDN Web Docs][3])

This is the baseline I would now treat as the **implementation contract**, rather than continuing to expand the architecture indefinitely.
